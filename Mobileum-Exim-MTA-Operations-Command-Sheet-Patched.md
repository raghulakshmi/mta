# Mobileum Exim MTA Operations Command Sheet

**Purpose:** Quick operational and troubleshooting commands for the Mobileum Exim MTAs, intended for customer operations teams even when the monitoring dashboard is unavailable.

**Applies to:** `mta1.mobileum.com` and `mta2.mobileum.com`

> Most commands in this document are **read-only**. Commands that modify the Exim queue are isolated in the final **Queue Modification – Controlled Use Only** section.

---

# 1. Log, Evidence, Configuration, and State Locations

## 1.1 Exim SMTP / Mail Logs

| Purpose | Path | Notes |
|---|---|---|
| Main Exim transaction log | `/var/log/exim4/mainlog` | Primary source for message receipt, delivery, defer, TLS, routing, transport and completion events |
| Exim reject log | `/var/log/exim4/rejectlog` | SMTP/ACL rejection evidence such as relay denied, invalid recipient and protocol rejection |
| Exim panic log | `/var/log/exim4/paniclog` | Serious Exim errors; should normally be empty or absent |
| Rotated main logs | `/var/log/exim4/mainlog.1`, `/var/log/exim4/mainlog.*.gz` | Historical mail transactions |
| Rotated reject logs | `/var/log/exim4/rejectlog.1`, `/var/log/exim4/rejectlog.*.gz` | Historical rejection evidence |
| Rotated panic logs | `/var/log/exim4/paniclog.*` | Historical critical Exim errors if any |

> For historical searches, always include rotated logs. A message may no longer exist in the current queue but will normally still be traceable in `mainlog*`.

## 1.2 Exim Queue / Spool State

| Purpose | Path |
|---|---|
| Exim spool root | `/var/spool/exim4/` |
| Queued message input files | `/var/spool/exim4/input/` |
| Per-message spool logs | `/var/spool/exim4/msglog/` |
| Exim spool database | `/var/spool/exim4/db/` |

> Do **not** count files under `/var/spool/exim4/input/` to determine queue depth. One queued message can use multiple spool files. Use `exim -bpc`.

# 2. Recommended Shell Helper

To avoid repeatedly typing the Mobileum Exim configuration path, define this helper after logging in to an MTA:

```bash
exim_mta() {
  sudo exim4 \
    -C /etc/exim4/exim4.conf.mobileum-safehold \
    "$@"
}
```

Examples:

```bash
exim_mta -bpc
exim_mta -bp
exim_mta -Mvl MESSAGE-ID
```

The helper exists only in the current shell session.

# 5. Queue Summary

## 5.1 Number of Queued Messages

```bash
exim_mta -bpc
```

Example:

```text
13
```

This means 13 messages are currently in the Exim queue.

## 5.2 Show All Queued Messages

```bash
exim_mta -bp
```

Example:

```text
3m   352 1x8Gsc-00000000Zxe-1NfG <test@mta1.mobileum.com> *** frozen ***
          Venkatesh.AK@mobileum.com
```

### How to Read a Queue Entry

| Field | Meaning |
|---|---|
| `3m` | Message has been in the queue for approximately 3 minutes |
| `352` | Approximate message size in bytes |
| `1x8Gsc-00000000Zxe-1NfG` | Exim Message-ID; this is the primary trace identifier |
| `<test@mta1.mobileum.com>` | Envelope sender |
| `*** frozen ***` | Exim will not automatically retry/deliver this message until it is thawed |
| `Venkatesh.AK@mobileum.com` | Envelope recipient |

### Important Queue Status Meanings

**Frozen**

```text
*** frozen ***
```

Exim has intentionally stopped automatic delivery attempts for that message. During the Mobileum safe-hold/testing phase, `frozen by ACL` is expected. In production, unexpected frozen messages require investigation.

**Null Sender**

```text
<>
```

The envelope sender is empty. This is normally a DSN/bounce message and is valid SMTP behaviour.

**Queued**

A message shown by `exim -bp` exists in the Exim queue/spool and has not yet fully completed processing.

**Deferred**

A delivery attempt temporarily failed and Exim intends to retry according to retry rules. Deferrals are normally identified in `mainlog` with:

```text
==
```

**Completed**

A `Completed` entry in `mainlog` means Exim has finished processing that message and removed it from its active queue.

# 6. Exim Main Log Symbols

These symbols are fundamental when reading `/var/log/exim4/mainlog`.

| Symbol / Text | Meaning |
|---|---|
| `<=` | Message received/accepted by Exim |
| `=>` | Successful delivery to a recipient/transport |
| `==` | Delivery deferred; Exim will retry |
| `**` | Delivery permanently failed |
| `Completed` | Exim completed processing and removed the message from the queue |
| `R=` | Router used |
| `T=` | Transport used |
| `H=` | Remote host |
| `X=TLS...` | TLS was used for that SMTP delivery |
| `C="250 ..."` | Remote SMTP response text |

Example successful downstream delivery:

```text
=> user@mobileum.com R=proofpoint_copy T=proofpoint_smtp H=...
```

Example deferred delivery:

```text
== user@mobileum.com ... temporarily deferred
```

Example permanent delivery failure:

```text
** user@example.com ...
```

# 16. Reliable Historical Log Search Helpers

Because `/var/log/exim4/` may not be directly readable by the normal login shell, these helper functions let `root` expand and read current and rotated Exim logs.

```bash
mainlog_search() {
  sudo bash -c \
    'zgrep -hFi -- "$1" /var/log/exim4/mainlog* 2>/dev/null' \
    _ "$1"
}

rejectlog_search() {
  sudo bash -c \
    'zgrep -hFi -- "$1" /var/log/exim4/rejectlog* 2>/dev/null' \
    _ "$1"
}

message_trace() {
  sudo bash -c \
    'zgrep -hF -- "$1" /var/log/exim4/mainlog* /var/log/exim4/rejectlog* 2>/dev/null' \
    _ "$1"
}
```

These search current and rotated logs, including compressed `.gz` files.

# 19. Historical Search by Sender + Recipient Combination

Set both addresses:

```bash
SENDER='sender@example.com'
RCPT='Venkatesh.AK@mobileum.com'
```

Find Message-IDs received from the sender, then display only transactions that also contain the target recipient:

```bash
for ID in $(
  mainlog_search "$SENDER" \
    | grep ' <= ' \
    | awk '{print $3}' \
    | sort -u
); do
  if message_trace "$ID" | grep -Fqi "$RCPT"; then
    echo
    echo "===== MATCH: $ID ====="
    message_trace "$ID"
  fi
done
```

This is the recommended command-line workflow when a Mobileum employee says:

> “I did not receive an email from `sender@example.com`.”

It correlates by Exim Message-ID rather than assuming sender and recipient must appear on the same log line.

# 23. Prove One Message Reached Both Proofpoint and Barracuda

```bash
ID='1x8aP2-00000003RHs-2Skb'

message_trace "$ID" \
  | grep -E 'R=proofpoint_copy|R=barracuda_production|Completed'
```

For a successful dual-delivery production transaction, the operator should see both:

```text
R=proofpoint_copy
R=barracuda_production
```

and normally a later:

```text
Completed
```

Interpretation:

- `R=proofpoint_copy` proves the Proofpoint router/leg was used.
- `R=barracuda_production` proves the Barracuda production router/leg was used.
- `Completed` proves Exim completed its processing of the message and removed it from the queue.

For stronger evidence, inspect the complete lines. A successful delivery line normally begins with:

```text
=>
```

and includes the router, transport, destination host, TLS information if used, and the remote SMTP response.

# 24. Successful Delivery, Deferred Delivery, Failure, and Completion

Successful delivery:

```bash
sudo grep ' => ' /var/log/exim4/mainlog | tail -100
```

Meaning:

```text
=>   successful delivery
```

Deferred delivery:

```bash
sudo grep ' == ' /var/log/exim4/mainlog | tail -100
```

Meaning:

```text
==   temporary delivery failure; Exim will retry
```

Common causes include connection timeout, connection refused, temporary remote SMTP `4xx`, DNS problems, TLS negotiation issues, or downstream unavailability.

Permanent delivery failure:

```bash
sudo grep ' \*\* ' /var/log/exim4/mainlog | tail -100
```

Meaning:

```text
**   permanent delivery failure
```

Completed messages:

```bash
sudo grep ' Completed' /var/log/exim4/mainlog | tail -100
```

Meaning:

> Exim finished processing the message and removed it from the active queue.

# 32. Operational Troubleshooting Workflows

## 32.1 Employee Says: “I Did Not Receive an Email”

Example:

```text
Recipient: Venkatesh.AK@mobileum.com
Sender:    sender@example.com
```

Recommended workflow:

1. Search historical main logs by recipient:

   ```bash
   mainlog_search 'Venkatesh.AK@mobileum.com'
   ```

2. Search by external sender:

   ```bash
   mainlog_search 'sender@example.com'
   rejectlog_search 'sender@example.com'
   ```

3. If a Message-ID is found, trace it:

   ```bash
   ID='EXIM-MESSAGE-ID'
   message_trace "$ID"
   ```

4. Determine which state applies:

   - sender never reached MTA;
   - SMTP transaction rejected;
   - message accepted;
   - message frozen/safe-held;
   - message deferred;
   - message delivered to Proofpoint;
   - message delivered to Barracuda;
   - message permanently failed;
   - message completed.

5. If required, prove both downstream delivery legs:

   ```bash
   message_trace "$ID" \
     | grep -E 'R=proofpoint_copy|R=barracuda_production|Completed'
   ```

## 32.2 External Sender Says: “I Sent the Email”

```bash
mainlog_search 'sender@example.com'
rejectlog_search 'sender@example.com'
```

If no receive or reject evidence exists, that MTA has no log evidence that the sender connected/submitted the message during the retained log period.

If a Message-ID exists:

```bash
message_trace 'MESSAGE-ID'
```

Then identify recipient and final disposition.

## 32.3 Queue Is Growing

```bash
exim_mta -bpc
exim_mta -bp
sudo exiwhat
df -hT /var/spool/exim4
df -i /var/spool/exim4
free -h
uptime
```

Then check deferrals:

```bash
sudo grep ' == ' /var/log/exim4/mainlog | tail -100
```

Proofpoint:

```bash
sudo grep 'R=proofpoint_copy' /var/log/exim4/mainlog | tail -50
```

Barracuda:

```bash
sudo grep 'R=barracuda_production' /var/log/exim4/mainlog | tail -50
```

Panic log:

```bash
sudo test -s /var/log/exim4/paniclog \
  && sudo tail -100 /var/log/exim4/paniclog \
  || echo "paniclog empty/not present"
```

## 32.4 Verify Dual-Delivery Integrity for One Message

```bash
ID='MESSAGE-ID'

message_trace "$ID" \
  | grep -E 'R=proofpoint_copy|R=barracuda_production|Completed'
```

The operator should see both:

```text
R=proofpoint_copy
R=barracuda_production
```

For successful delivery, inspect the complete `=>` lines and confirm the downstream SMTP response is successful, normally `250`.

## 32.5 SMTP Listener Appears Down

```bash
systemctl status exim4-mobileum-safehold --no-pager
sudo ss -lntp '( sport = :25 )'
sudo journalctl -u exim4-mobileum-safehold -n 100 --no-pager
```

Then check the panic log and validate Exim configuration:

```bash
sudo test -s /var/log/exim4/paniclog \
  && sudo tail -100 /var/log/exim4/paniclog \
  || echo "paniclog empty/not present"

exim_mta -bV
```

# 36. Key Operational Interpretation

A healthy production MTA should normally have:

- the approved Mobileum Exim service active;
- TCP/25 listening on the intended MTA interface;
- low/controlled queue depth;
- no unexpected frozen messages;
- no sustained queue growth;
- adequate spool disk and inode headroom;
- no meaningful entries in `paniclog`;
- successful Proofpoint and Barracuda delivery evidence;
- successful downstream SMTP `250` responses;
- TLS visible where required;
- no sustained increase in deferrals or permanent failures;
- CPU, load and memory within normal operating range.

For any specific message, the **Exim Message-ID** should be treated as the primary troubleshooting key.

# 39. Queue Summary with `exiqsumm`

The normal queue commands remain:


For a summarized queue view:

```bash

```

`exiqsumm` is useful when the queue is large because it summarizes queued mail rather than printing every message individually.

Check that it exists:

```bash

```

## Exim Message-ID vs RFC `Message-ID:`

Do not confuse these two identifiers.

Example **Exim Message-ID**:

```text
1x7Ux3-000000000rS-2RyL
```

This ID is assigned by Exim and is the primary identifier in Exim queue and transaction logs.

An RFC mail header can instead look like:

```text
Message-ID: <abc123@example.com>
```

That value was supplied/generated as part of the email itself. Both can be useful, but they are not interchangeable.

## 46.1 Check SMTP Capabilities Locally

## 46.2 Local STARTTLS Handshake

```bash

  -brief </dev/null
```

Full certificate chain:

```bash
openssl s_client \
  -starttls smtp \

```

## 46.3 Inspect the Local SMTP Certificate

If the configured certificate path is `/etc/exim4/tls/server.crt`:

```bash

  -in /etc/exim4/tls/server.crt \
  -noout \
  -subject \
  -issuer \
  -dates \
  -ext subjectAltName
```

## 46.4 Verify Exim Can Read the Certificate and Key

```bash
sudo -u Debian-exim \
  test -r /etc/exim4/tls/server.crt \
  && echo "CERT readable"

sudo -u Debian-exim \
  test -r /etc/exim4/tls/server.key \
  && echo "KEY readable"
```

## 46.5 Verify Certificate / Private-Key Pair

```bash
sudo openssl x509 \
  -in /etc/exim4/tls/server.crt \
  -pubkey -noout \
  | sha256sum

sudo openssl pkey \
  -in /etc/exim4/tls/server.key \
  -pubout \
  | sha256sum
```

The two hashes should match.

> If the configured TLS file paths differ, obtain the effective values from the Mobileum Exim configuration before using these commands.

# 54. Jumpbox Dashboard Recovery

Use this procedure if the green MTA status dots disappear, the dashboard shows `STALE`, or `/api/health` returns HTTP 500.

These actions restart only monitoring components on the Jumpbox. They do **not** restart Exim and do **not** modify either MTA queue.

## 54.1 STALE / Missing Green Dots

Check health:

```bash
curl -s http://127.0.0.1:8089/api/health \
  | python3 -m json.tool
```

Check the collector:

```bash
sudo journalctl \
  -u mobileum-mta-collector \
  --since "10 minutes ago" \
  --no-pager
```

If stale collection or errors such as these appear:

```text
[Errno 24] Too many open files
unable to open database file
```

restart only the collector:

```bash
sudo systemctl restart mobileum-mta-collector
sleep 30
```

Then recheck:

```bash
curl -s http://127.0.0.1:8089/api/health \
  | python3 -m json.tool
```

Healthy output should show:

```text
"display_status": "UP"
"host_reachable": true
"exim_service": "active"
"listener": 1
"sample_age_seconds": less than 45
```

## 54.2 `/api/health` Returns HTTP 500

Confirm:

```bash
curl -i http://127.0.0.1:8089/api/health
```

Inspect backend logs:

```bash
sudo journalctl \
  -u mobileum-mta-dashboard \
  --since "10 minutes ago" \
  --no-pager
```

Restart the dashboard backend if required:

```bash
sudo systemctl restart mobileum-mta-dashboard
sleep 5
```

Then verify:

```bash
curl -i http://127.0.0.1:8089/api/health
```

Expected:

```text
HTTP/1.1 200 OK
```

## 54.3 Optional File-Descriptor Capture Before Restart

When `[Errno 24] Too many open files` appears, capture this before restarting if time permits:

```bash
CPID=$(systemctl show \
  -p MainPID \
  --value mobileum-mta-collector)

echo "Collector PID: $CPID"

sudo ls /proc/$CPID/fd | wc -l
sudo grep -i 'open files' /proc/$CPID/limits
sudo systemctl show mobileum-mta-collector -p LimitNOFILE
```

This evidence is useful for diagnosing a recurring collector file-descriptor problem.
